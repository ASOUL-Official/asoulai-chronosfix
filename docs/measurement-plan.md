# A-CFX 测量与商业验证计划

本文件严格区分“仓库当前已经测得的工程事实”和“需要真实用户/环境才能完成的商业指标”。当前没有客户试点、生产事故对照或付费数据，因此不声明 MTTR 降幅、节省金额、客户转化率或 ROI 已经实现。

## 1. 当前已测工程事实

| 指标 | 当前证据 | 属性 |
|---|---|---|
| 主场景端到端耗时 | `engineering-metrics.json.elapsed_ms` | 本地 wall-clock 实测 |
| Span duration | `trace.jsonl.duration_ms` | 本地实测；instant event 单独标记 |
| 步骤完成率 | 由 Trace status 推导 | derived，不是外部工具成功率 |
| 证据覆盖率 | 由必需声明/产物计算 | derived |
| 外部工具成功率 | null | 本地运行没有调用外部工具 |
| 受支持诊断 | 9/9 | 合成、限定模型范围 |
| 整体达成预期 | 10/12 | 合成、包含 2 个未支持漏诊 |
| 正确拒答 | 1/1 | 合成；相同干预冲突由可辨识性仲裁拒答 |
| 回滚验证 | 主场景通过 | 本地状态字段往返校验 |
| 证据完整性 | run manifest + SHA-256 | 本地文件绑定 |

上述结果不能外推为生产 MTTR、真实故障准确率或商业 ROI。

## 2. 正确性测量计划

目标：确认系统能区分主因、放大因素、非因果变化和证据不足。

| 指标 | 计算方式 | 计划数据 |
|---|---|---|
| 根因命中率 | observed primary 与专家 Ground Truth 完全一致 | 先用合成集，后用 5–10 个脱敏历史事故 |
| 误归因率 | 非主因被错误宣称为 primary 的比例 | 干扰项 Badcase |
| 拒答准确率 | 证据不足时是否 abstain | 冲突、缺失、工具失败场景 |
| 证据完整度 | 因果、验证、风险、回滚、缺口、完整性摘要是否齐全 | Evidence Passport / run manifest |

## 3. 变更可信度测量计划

| 指标 | 计算方式 |
|---|---|
| 强制变体通过率 | selected patch 健康的 mandatory variants / 全部 mandatory variants |
| 最差失败率/P99 | 全部强制变体的最大值 |
| 回滚完整率 | 具备 machine-readable rollback 且恢复基线的补丁比例 |
| 质量门禁准确性 | 失败变体、缺失声明、未执行检查是否均 fail-closed |
| PR 可审查度 | 本地草案是否包含场景、真实 changes、rollback、执行检查和审批记录 |

## 4. 人工 baseline 对照计划

选择 5–10 个同难度事故，让同一批参与者分别使用现有工具链和 A-CFX，随机化任务顺序并记录：

- MTTA：从收到事故到提出候选主因；
- 可审查方案耗时：从收到事故到形成含因果、验证、风险、回滚的 PR 材料；
- 根因正确性和误归因；
- 人工编辑 Evidence Passport 的时间；
- 审批人理解证据所需时间；
- 回滚演练是否成功。

报告必须披露参与人数、经验水平、场景数量、计时方法、中位数/P90 和失败样例；样本过小时只报告观察值，不做统计显著性宣传。

## 5. 商业验证计划

| 商业假设 | 验证方式 | 成功门槛由谁确认 |
|---|---|---|
| 研发团队愿意为“事故到 PR 证据”付费 | 访谈与可用性测试，记录是否愿意进入试点 | 目标客户，不由团队自评 |
| 审计行业重视 Evidence Passport | 让发布/合规人员评价字段完整度和可追责性 | 发布负责人/审计人员 |
| DevOps 平台可低成本集成 | 接一个真实 Git/CI/Trace 组合，统计适配工作量 | 联合试点团队 |
| 故障资产可复用 | 同一故障基因包跨相邻服务回放 | 以通过/失败数据判断 |

收费方式（SaaS、私有化、云市场插件、审计模块）目前都是候选商业模型，不是已验证收入。

## 5.1 复赛一键验收证据

`scripts/run_semifinal_acceptance.py` 在隔离临时目录中顺序执行：36 项测试、严格 JSON/JSONL 校验、公开 Draft 2020-12 Schema、AgentTeams v1beta1 资源校验、人工已审批通过分支、无人审批 fail-closed 分支、12 场景评测和 Demo JavaScript 语法检查。脚本会分别断言 `approved`、`blocked-awaiting-human`、9/9 支持范围诊断、1/1 正确拒答和 8 个 Worker。

GitHub Actions 将上传该验收器生成的 JSON/Markdown 作为构建产物。它证明的是可复现工程闭环，不替代真实 AgentTeams Controller、云端 Skill 或生产事故数据。
